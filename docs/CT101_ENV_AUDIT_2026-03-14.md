# CT101 environment audit — 2026-03-14

## Executive summary

If the goal is **"make CT101 as close as possible to its previous working state"**, there are really two different restore scopes:

1. **OpenClaw state** (`/root/.openclaw`)
2. **Whole CT101 runtime behavior** (systemd units, Docker containers, Compose files, cron, ad-hoc scripts, PM2-managed processes, container-local code)

A clean OpenClaw restore can address **(1)**.
It will **not automatically recover (2)**.

The good news:

- host OpenClaw autostart is currently on solid footing via **systemd user service**
- observability stack autostart is also declarative and reasonably recoverable

The bad news:

- the old `gladys-clawdbot` stack is **not declarative anymore**
- it is a stale/orphaned Docker container with a manual/PM2-driven process garden inside it
- important parts of that setup are **not represented in the current host Compose file**
- some of the old startup path appears to depend on a **broken shell profile** and **no saved PM2 dump**

So the safest path is:

1. **capture the fragile container state before any restart/recreate**
2. restore OpenClaw separately and safely
3. then decide whether to preserve the old `gladys-clawdbot` shape or replace it with a cleaner design

## 1) What is currently robust and likely to survive

### OpenClaw on the host

Current host OpenClaw is in a good state from a service-management perspective:

- service manager: **systemd user service**
- unit: `openclaw-gateway.service`
- enabled: **yes**
- running: **yes**
- RPC probe: **ok**
- user lingering: **yes** (`loginctl show-user root -p Linger` → `Linger=yes`)

The unit file is explicit and healthy:

- `Restart=always`
- `RestartSec=5`
- config path: `~/.openclaw/openclaw.json`

That means **host OpenClaw autostart does not depend on PM2** and is already better than a hand-rolled PM2 approach.

### Observability stack

Root crontab currently contains:

- every 2 minutes: `/usr/local/bin/observability-autorecover.sh`
- `@reboot`: `docker compose -f /root/observability/docker-compose.observability.yml up -d`
- `@reboot`: rerun `observability-autorecover.sh`

This is host-declared and recoverable.

### Stable Docker services

These are currently up with restart policies and appear structurally recoverable:

- `otel-collector` — `unless-stopped`
- `blackbox-exporter` — `unless-stopped`
- `cloudflared` — `unless-stopped`
- `signoff-dashboard` — `unless-stopped`
- `portainer` — `always`
- `formbricks-db` — running
- `formbricks-redis` — running

## 3) The big risk area: `gladys-clawdbot`

This is the main reason I cannot promise “restore CT101 and everything will just come back” from an OpenClaw state restore alone.

### What exists now

There is a running container:

- name: `gladys-clawdbot`
- image: `node:22-bookworm`
- restart policy: `unless-stopped`
- status: running

But its configured container command is effectively idle:

- PID 1 is `tail -f /dev/null`

That means the container restart policy only guarantees that **the idle container** comes back.
It does **not** by itself guarantee that the actual app stack inside comes back.

### What is actually running inside the container

Inside the running container, I found live processes such as:

- a **PM2 daemon**
- a Node app under `/root/clawd`
- a Python/Uvicorn stack under `/root/cortex_server`
- `cloudflared`
- a git-sync loop under `/opt/clawdbot/sync`
- a separate TypeScript operational HTTP server process

So this container is not a simple single-service container. It is a hand-built multi-process environment.

### Why this is fragile

#### A. The current Compose file does not reproduce it

The container labels say it belongs to Compose project `clawdbot` with config file:

- `/opt/clawdbot/docker-compose.yml`

But the **current** `/opt/clawdbot/docker-compose.yml` resolves to **`kokoro-tts`**, not `clawdbot`.

So `gladys-clawdbot` is effectively a **stale/orphaned container from an older Compose definition**.

If that container is removed and recreated from the current file, it will **not** come back as the same thing.

#### B. There are at least three generations of “clawdbot” config on disk

I found:

1. **Current** `/opt/clawdbot/docker-compose.yml`
   - no longer matches the running `gladys-clawdbot` service
2. **Saved older file** `/opt/clawdbot/docker-compose.yml.save`
   - old `node:22-bookworm`-based `clawdbot`
   - installs/runs app at container start
   - contains inline secret env values
3. **Newer separate file** `/opt/clawdbot/data/docker-compose.yml`
   - defines a different `ghcr.io/moltbot/moltbot:latest` style service
   - uses `.env`

So the historical setup has drifted across multiple models and is not cleanly represented in one source of truth.

#### C. PM2 inside the container is not reliably restorable

Inside the container:

- a PM2 daemon is running
- but `pm2` is not even resolvable from a clean shell PATH the way you’d expect
- there is **no** `/root/.pm2/dump.pm2`

That means there is **no clean saved PM2 process list** to resurrect from.

#### D. The shell startup path is broken

Container shell startup files include logic that sources:

- `$HOME/.local/bin/env`

But that file is missing.

After that, the shell file tries to run:

- `pm2 resurrect`

Because the earlier source step fails, this startup path is unreliable/broken.

So even if the plan was “PM2 will just resurrect everything,” the container’s own shell config does not support that confidently.

#### E. Important app paths are not host-mounted

The running workloads reference paths like:

- `/root/clawd`
- `/root/cortex_server`
- `/etc/pmhnp`
- `/opt/clawdbot/sync`

On the host, those corresponding paths are **missing**.

The only host binds declared for the container are:

- `/opt/clawdbot/data -> /root/.clawdbot`
- `/opt/clawdbot/config -> /config`

So the code/scripts/process topology for the live multi-process setup are **not being fully sourced from the host**.
That means part of the “old working state” effectively lives in the container layer / manual mutations, not in reproducible host files.

### Conclusion for `gladys-clawdbot`

`gladys-clawdbot` is **present**, but it is **not safely reproducible** from the current host config.

It may continue to work **as long as the current container instance stays alive**.
But I would **not** trust a fresh recreate, restart, or rebuild of that container to bring the same stack back automatically.

## 4) What an OpenClaw restore would and would not recover

### A proper OpenClaw restore can recover

- `/root/.openclaw` state
- sessions
- workspaces
- agent state
- channel credentials *if the backup is complete*
- `openclaw.json`
- OpenClaw memory / cron / devices / identity under that state tree

### A proper OpenClaw restore will not automatically recover

- host Docker topology drift
- stale/orphaned containers
- PM2-managed processes inside `gladys-clawdbot`
- container-local code not mounted from host
- broken shell startup hacks
- Formbricks / groq-proxy failures
- Compose file drift across old/new clawdbot definitions

## 5) Best interpretation of “previous state”

If by “previous state” you mean:

### A. Previous **OpenClaw** state

Yes — that is realistic and we already have the guarded restore tooling for it.

### B. Previous **whole CT101 operating shape**

Only partially — because some of the prior behavior now appears to depend on a fragile container instance, not a clean declarative host setup.

So the right goal is:

- **restore OpenClaw cleanly**
- **preserve/snapshot the fragile container as-is before touching anything risky**
- then either:
  - keep that container alive while we normalize around it, or
  - replace it with a cleaner declarative setup

## 6) What I recommend next

### Priority 1 — capture the fragile parts before any restart/recreate

Before any host reboot or container recreation, capture:

- `docker inspect gladys-clawdbot`
- `docker inspect` for all containers
- a tarball of:
  - `/opt/clawdbot`
  - `/opt/formbricks`
  - `/root/observability`
- ideally a **container snapshot** of `gladys-clawdbot`
  - e.g. `docker commit` and/or `docker export`

Why: that container currently contains non-declarative state/process assumptions we may not be able to reconstruct later.

### Priority 2 — restore OpenClaw separately and safely

Use the guarded restore flow only for the proper OpenClaw state source.
That should not be used as a stand-in for the entire host environment.

### Priority 3 — choose between “preserve old clawdbot” and “better setup”

#### Preserve old behavior

If the goal is maximum continuity, then:

- treat `gladys-clawdbot` as a legacy pet container
- snapshot it first
- avoid recreating it until we have a reproducible spec

#### Better setup

If the goal is “same capabilities, but saner,” then the better design is:

- keep **OpenClaw** on host **systemd** (already good)
- move custom services out of the `tail -f /dev/null` + PM2 container pattern
- run each service via either:
  - proper Docker Compose with explicit command + mounted state, or
  - dedicated systemd units on the host
- keep secrets in env files / secret stores, not inline in Compose files
- keep startup scripts and configs versioned on the host, not trapped in a mutable container layer

That would be **better than the previous setup**, but it is a separate cleanup project — not something a backup restore alone can guarantee.

---

## 7) Bottom line

### Already solid

- host OpenClaw autostart via systemd
- host observability autostart via cron + Compose

### Recoverable with the right OpenClaw backup

- host `/root/.openclaw` state

### Not reliably recoverable from an OpenClaw restore alone

- old PM2-based `gladys-clawdbot` behavior
- container-local scripts/code/processes
- broken Formbricks / groq-proxy stack health

### Most important practical conclusion

If we want the **closest possible previous CT101 state**, the next safest action is:

1. snapshot `gladys-clawdbot` and key host config dirs
2. then do the guarded OpenClaw restore
3. then decide whether to preserve or redesign the legacy clawdbot container stack
