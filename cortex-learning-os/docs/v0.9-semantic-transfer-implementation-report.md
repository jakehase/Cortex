# v0.9 Semantic Transfer Implementation Report

## Scope

v0.9 implements a production-shaped but initially inert semantic math-to-code transfer bridge. The runtime default is enabled `active` mode, but the shipped and initialized transfer registry contains zero entries. Therefore the release cannot add transfer context until a later, separately authorized profile qualification and promotion succeeds.

This release does not claim that mathematical learning has transferred to coding, that either declared profile improves code, or that any profile is qualified.

## Implemented surfaces

- Two digest-bound declared hypotheses: `exact-multiplication` and `algebra-factoring`.
- A separate signed 36-concept transfer state; mathematical mastery never backfills it.
- A separate signed transfer registry and trust root, initialized empty.
- Enumerated code-first semantic matchers with observable assumptions and hard negative gates.
- Active runtime selection that requires a signed, qualified, enabled, unexpired entry and otherwise returns no context.
- Content-free, owner-only, bounded transfer telemetry isolated from lesson telemetry.
- Frozen signed qualification plans with run-seeded, balanced two-arm order and a provider/model/reasoning/read-only/tool-free runtime contract.
- A secretless qualification worker with fresh ephemeral calls, tool-event rejection, positive-usage evidence, crash-safe keyed resume, content-free provider ledgers, inert proposals, and exact manifests.
- Independent control-plane plan authentication, provider-ledger validation, deterministic oracle replay, threshold evaluation, signed state application, and separate promotion.
- Strict exact-product and polynomial-identity/root oracles; the polynomial oracle binds exactly two monic linear factors to exactly two verified roots.
- Immediate profile and registry disable/revoke operations plus the plugin-level transfer kill switch.

## Truth layers

The implementation keeps these records and claims separate:

1. mathematical mastery or review state;
2. declared transfer profile validity;
3. empirical paired qualification outcome for an exact profile/task/runtime;
4. signed transfer-state application;
5. signed-registry promotion and enablement;
6. per-prompt active context application;
7. broad or durable coding benefit, which this release does not establish.

Implementation tests and fake-adapter fixtures exercise mechanics only. They cannot qualify a profile. A real qualification additionally requires the signed frozen runtime, a complete provider/model call ledger, positive provider-observed input/output usage, zero observed tool events, exact task/arm coverage, and every declared gate.

- Existing signed math mastery and lesson registries: preserved independently.
